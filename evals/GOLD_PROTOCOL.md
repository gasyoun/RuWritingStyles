# Протокол золотого стандарта (GOLD) для санскритских eval-кейсов

Этот файл задает, **как** санскритские оценочные кейсы (`tags: ["GOLD_SANSKRIT"]`
в `evals/manifest.json`) становятся золотым стандартом, пригодным для измерения
качества разных провайдеров (Anthropic / OpenAI / Google) и для статей о
методике. Завершает пункт «золотой стандарт» фазы 3 дорожной карты
[../docs/roadmap-sanskrit-dh.md](../docs/roadmap-sanskrit-dh.md).

## Два класса кейсов

| Класс | Тег | Кто проверяет | Зависит от провайдера |
|---|---|---|---|
| Детерминированные | `deterministic` | автоматически (линтер транслитерации, проверка цитирований) | нет — проходят одинаково на любом провайдере, включая `mock` |
| Экспертные (LLM-judgment) | (без `deterministic`) | ≥2 эксперта-разметчика | да — содержательная находка появляется только на реальном провайдере |

Детерминированные кейсы — это регрессионные тесты инфраструктуры: они входят в
GitHub-workflow `Eval Smoke` и проходят на `--provider mock`. Экспертные кейсы —
это собственно золотой стандарт: на `mock` они **не** проходят (заглушка не дает
содержательных находок), их назначение — оценка реальных провайдеров.

## Каждый кейс

Кейс в `evals/manifest.json` объявляет:

- `input` — документ с **одной** заведомо заложенной ошибкой
  (`examples/input/<id>.md`);
- `default_styles` — стили-ревьюеры, которые должны ее поймать;
- `expected_risks` / `scoring.required_finding_types` — тип находки, который
  считается верным срабатыванием (например `unsupported_sanskrit_etymology`,
  `wrong_samasa_type`, `mistranslated_native_term`,
  `anachronistic_sanskrit_period`, `missing_commentary_layer`);
- `scoring.min_required_matches` — сколько требуемых типов должно совпасть
  (обычно 1).

Каждый тип находки в `required_finding_types` обязан существовать среди `checks`
соответствующего паспорта в `styles/passports/` — иначе ни один ревьюер не может
его выдать.

### Политика меток (`accepted_finding_aliases`)

Скорер требует **точного** совпадения строки типа находки — но недетерминированная
модель иногда выдает концептуально верную ошибку под чуть иной меткой (прогон
2026-06-30: `sanskrit-pseudo-etymology` нашел проблему, но пометил ее
`unsupported_etymology` вместо ожидаемого `unsupported_sanskrit_etymology` →
формальный незачет при верной детекции). Чтобы не ослаблять протокол до
substring-совпадения (`unsupported.*etymology` поймало бы и мусор), у каждого
кейса есть карта псевдонимов:

```json
"scoring": {
  "required_finding_types": ["unsupported_sanskrit_etymology"],
  "accepted_finding_aliases": {
    "unsupported_sanskrit_etymology": ["unsupported_etymology", "pseudo_etymology"]
  }
}
```

Канонический требуемый тип считается пойманным, если среди находок присутствует
он **сам или любой из его псевдонимов**. `matched_required_finding_types` всегда
записывает **канонический** тип (не псевдоним), поэтому таблицы сопоставимы между
прогонами. Псевдонимы задаются точечно и обоснованно (наблюденное или заведомо
эквивалентное обозначение), а не как расширение вокабуляра под конкретный прогон.
Заменяет захардкоженный псевдоним из коммита `7dbbcc4`; все 5 экспертных кейсов
переведены на эту схему.

## Разметка экспертами (золотой стандарт)

1. **Минимум два независимых разметчика** на каждый экспертный кейс. Требуемая
   квалификация: чтение санскрита и знакомство с грамматической традицией
   (вьякарана) и/или ведийской филологией.
2. Разметчик получает: текст кейса (`input`), описание заложенной ошибки
   (`purpose`) и вывод реального прогона (`runs/<suite>-<id>/`: `reviews/*.json`,
   `council.json`, `verification.json`). Разметчик **не** видит оценок другого
   разметчика.
3. Разметчик отвечает по каждому кейсу:
   - **поймана ли заложенная ошибка** (да / нет / частично);
   - **верен ли тип находки** (совпадает ли с `required_finding_types`);
   - **нет ли ложных срабатываний** (находки не по делу).
4. **Согласие разметчиков (inter-rater agreement).** Фиксируется доля совпадений
   и/или каппа Коэна. Расхождения разрешаются обсуждением; при неустранимом
   расхождении привлекается третий разметчик, решение — по большинству.
5. **Согласие на запись.** Разметчики дают согласие на хранение своих суждений
   (обезличенно: «разметчик A / B») в аудит-файле кейса. Персональные данные не
   публикуются.

Итог разметки по каждому экспертному кейсу хранится рядом с прогоном как
`gold-annotation.json` со схемой:

```json
{
  "case_id": "karaka-not-padezh",
  "provider": "anthropic",
  "raters": ["A", "B"],
  "caught": true,
  "type_correct": true,
  "false_positives": 0,
  "agreement": 1.0,
  "notes": "оба разметчика отметили смешение караки и падежа"
}
```

## Прогон и бенчмарк

Детерминированные кейсы (бесплатно, без ключей):

```bash
rws eval-suite --provider mock --suite-id gold-det
```

Экспертные кейсы — на реальном провайдере (платно, решение автора):

```bash
rws eval-suite --provider anthropic --suite-id gold-anthropic
rws eval-suite --provider google    --suite-id gold-google
rws eval-compare runs/gold-anthropic runs/gold-google
```

Сводная таблица точности по типам находок и провайдерам публикуется в
`docs/benchmark.md` **после** того, как принято решение о платном прогоне и
проведена экспертная разметка. До этого момента раздел остается пустым — числа
без разметки не являются золотым стандартом.

### Усреднение по N прогонам (обязательно для слоя 1)

DeepSeek недетерминирован: зачет одного прогона осциллировал 1/5 → 2/5 → 3/5 →
0/5 на неизменном коде. Поэтому **single-run accuracy запрещена как метрика** —
слой-1 числа приводятся только как pass-rate по ≥5 прогонам с разбросом:

```bash
# один кейс, N=5 прогонов -> агрегат:
rws eval-run --case sanskrit-pseudo-etymology --provider deepseek --repeat 5
# все кейсы манифеста, N=5 -> суммарный агрегат:
rws eval-suite --provider deepseek --repeat 5
```

Агрегат (`runs/<agg-id>/eval-aggregate.json`, схема
[../schemas/eval-aggregate.schema.json](../schemas/eval-aggregate.schema.json),
валидируется `rws validate-eval-aggregate`) дает по каждому кейсу: `pass_rate`,
`detection_rate` (доля прогонов, где ожидаемый тип пойман — независимо от
diff-лимитов), `diff_ok_rate`, распределение `verification_status` и
среднее/σ/min/max по `char_delta_ratio` / `changed_line_ratio` / числу находок.
Разделение **detection-rate vs pass-rate** критично: детекция (нашла ли модель
ошибку) стабильна ≈1.0, а pass-rate хоронит over-rewrite ревизии (лечится
архитектурно в H073 span-patch), поэтому в статье эти два числа приводятся
раздельно.

**Воспроизводимость (temperature=0).** Провайдер принимает
`RWS_DEEPSEEK_TEMPERATURE=0`; probe-результат — в `docs/benchmark.md`. Сам N=5
бенчмарк выполняется при температуре по умолчанию, чтобы измерять реальный
недетерминизм, а не маскировать его.

## Критерий готовности фазы 3

- ≥10 санскритских кейсов в `evals/manifest.json` (детерминированные +
  экспертные); ✅ выполнено;
- протокол экспертной разметки задокументирован (этот файл); ✅ выполнено;
- проведен прогон на ≥2 реальных провайдерах с экспертной разметкой и
  опубликована таблица в `docs/benchmark.md`; ⏳ ждет решения о платном прогоне.
