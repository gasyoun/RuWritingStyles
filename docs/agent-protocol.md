# Протокол агентной редакции

Этот документ описывает, как разные стили RuWritingStyles должны проверять один документ, отвечать друг другу и участвовать в создании улучшенной версии.

## Основные роли

В агентном режиме есть четыре типа участников:

| Роль | Назначение |
|---|---|
| `style_reviewer` | Проверяет документ с точки зрения одного стиля и выдает замечания. |
| `style_respondent` | Читает замечания других стилей и отвечает на них. |
| `synthesizer` | Собирает согласованные замечания в новую редакцию документа. |
| `verifier` | Проверяет, что итоговая версия не исказила исходник. |

Один и тот же стиль может быть `style_reviewer` и `style_respondent`, но не должен быть финальным `synthesizer` для самого себя. Синтезатор должен видеть все голоса, а не продолжать один стиль.

## Раунд 1. Независимая проверка

Каждый стиль получает:

- паспорт стиля;
- полную карту документа;
- сегменты с `span_id`;
- задачу пользователя;
- ограничения запуска.

Стиль возвращает только структурированные замечания:

```json
{
  "style_id": "zalizniak-zametki",
  "summary": "Документ нуждается в явном различении внешнего сходства и исторического доказательства.",
  "findings": [
    {
      "id": "finding-001",
      "span_id": "p014",
      "severity": "major",
      "type": "unsupported_etymology",
      "finding": "Тезис строится на внешнем сходстве без исторических форм.",
      "suggestion": "Добавить ранние формы и регулярные фонетические соответствия.",
      "confidence": 0.82
    }
  ]
}
```

## Раунд 2. Доска замечаний

Оркестратор объединяет замечания по `span_id`, типу проблемы, близости формулировок и степени серьезности.

Цель доски: показать, где стили говорят об одном и том же, а где их требования расходятся.

## Раунд 3. Ответы стилей

Каждый стиль получает доску замечаний и отвечает только на те замечания, которые входят в его компетенцию.

Формат ответа:

```json
{
  "style_id": "zalizniak-shkolnikov_1",
  "replies": [
    {
      "reply_to": "finding-001",
      "position": "agree_with_modification",
      "comment": "Проверку нужно оставить, но формулировку следует сделать проще для неспециалиста.",
      "proposed_adjustment": "Сначала объяснить на простом примере, зачем нужны исторические формы."
    }
  ]
}
```

Разрешенные значения `position`:

| Значение | Смысл |
|---|---|
| `agree` | Стиль полностью согласен. |
| `agree_with_modification` | Стиль согласен, но предлагает изменить способ правки. |
| `disagree` | Стиль считает замечание вредным или неверным. |
| `needs_human_decision` | Требуется решение автора или редактора. |
| `out_of_scope` | Замечание не относится к компетенции этого стиля. |

## Раунд 4. Решение по правкам

Оркестратор присваивает каждому замечанию статус:

| Статус | Условие |
|---|---|
| `accepted` | Несколько стилей согласны, серьезных возражений нет. |
| `accepted_with_modification` | Замечание принято, но с уточнением другого стиля. |
| `rejected` | Замечание признано неверным или вредным. |
| `deferred` | Нужен человек или внешний источник. |
| `informational` | Замечание полезно для отчета, но не требует правки. |
| `deferred` | Нужен человек или внешний источник. |

## Разрешение конфликтов и Веса авторитетности

При наличии противоречивых рекомендаций от разных стилей (например, один требует упростить термин, а другой — сохранить его точность), Совет (Council) использует систему весов и Матрицу Конфликтов.

### 1. Веса доменов (Domain Boost)
Если тематика текста (`text_domain`) совпадает с профилем кластера, его голос получает **двойной вес (2.0x)**.
- Тема `etymology` -> Буст для `ling_iesh`.
- Тема `semiotics` -> Буст для `ling_mts`.
- Тема `literature` -> Буст для всех `lit_` кластеров.

### 2. Филологическая матрица конфликтов
Для классических споров между школами установлены приоритеты:
- **Bakhtin > OPOYAZ**: При конфликте формального анализа и полифонии смыслов приоритет отдается глубине смыслов.
- **IESH > NSS**: Этимологическая точность выше требований современной нормы.
- **Textology > Historico-Cultural**: Точность передачи источника выше культурологической интерпретации.

### 3. Эпистемическая прозрачность
Совет обязан указывать в поле `reason`, какая именно филологическая норма или правило матрицы было использовано для разрешения спора.

Синтезатор получает исходный документ, сегменты, доску замечаний, решения по правкам, задачу пользователя и ограничения на объем и стиль.

Синтезатор возвращает:

```json
{
  "revised_document": "...",
  "applied_changes": [
    {
      "span_id": "p014",
      "source_findings": ["finding-001"],
      "change_type": "strengthen_argument",
      "explanation": "Добавлена проверка исторических форм перед выводом о родстве."
    }
  ],
  "unresolved": [
    {
      "span_id": "p022",
      "reason": "Нужна внешняя библиографическая проверка."
    }
  ]
}
```

## Раунд 6. Проверка

Проверяющий получает исходник и новую версию. Он не должен улучшать стиль; его задача - найти искажения.

Проверяются:

- сохранность фактов;
- сохранность структуры аргумента;
- отсутствие неподтвержденных добавлений;
- выполнение согласованных замечаний;
- отсутствие чрезмерной стилизации;
- ясная маркировка нерешенных мест.

## Запреты

Агентам нельзя:

- переписывать весь документ без привязки к замечаниям;
- выдавать свободный диалог вместо JSON;
- ссылаться на несуществующие источники;
- заменять задачу пользователя собственной;
- выдавать стилистическое предпочтение за факт;
- стирать голос автора без явной причины;
- смешивать проверку, спор и финальное редактирование в одном шаге.

## Минимальный успешный запуск

Запуск считается успешным, если после него есть:

- `original.md`;
- `segments.json`;
- файлы `reviews/*.json` для выбранного набора стилей; текущий MVP-набор содержит 6 стилей;
- `council.json`;
- `revised.md`;
- `verification.json`;
- `report.md`;
- `summary.html`.

При полном `rws run --execute` также ожидаются производные артефакты качества и академического аппарата: `impact.json`, `syntax.json`, `report.tex` и `references.bib`.
